# GitHub access for PR Genie loops

Loop agents (implementor, reviewer, steward) must not run with your full GitHub account power. A spec that says “create a scratch repo on GitHub” must fail in the client hook, not on GitHub. **RAD-138** is the counterexample: a loop followed its EARS spec and ran `gh repo create`, which created `radiancelux/rad138-utf8-scratch`.

**Best-effort gate.** `github-gate.cjs` (`beforeShellExecution` / `beforeMCPExecution`) is a guard rail only. The fine-grained `GH_TOKEN` (below) is the real boundary. When Cursor delivers a well-formed hook payload, the gate allows read-only PR Genie MCP tools and returns **`permission: deny`** for agent human-only actions (`export_local_pr`, `record_export_gate_override`, `gh_use`, `clear_loop_cancel`, the CLI `prgenie export` / `prgenie gh use` / `prgenie export-gate-override`, …) for **every** agent, and denies `git push` / `gh pr create` / `gh pr merge` / `gh repo create` / `gh release create` and the RAD-163 repo-management commands for **PR Genie loop agents only** (RAD-190 loop-only scope, below). A normal agent (not in a loop worktree or an active steward loop) may `git push` and use `gh` normally; its token is its boundary. Humans export via **Open on GitHub** or `prgenie export` in their own terminal — those paths do not run through the agent hook. With the escape hatch off, **no gate path returns `ask`** (RAD-190, table below). When stdin is empty or not JSON, the gate **fails closed** (`permission: deny` with a clear reason — never silent `allow`).

**Escape hatch (RAD-188):** set `PRGENIE_GITHUB_GATE_ASK=1` in your environment (not via MCP) to restore `permission: ask` for human-only actions on hosts that still show a confirmation dialog. Defaults off. Any agent shell command that names the variable (any case) **and** writes environment or registry state gets **`deny`**: `setx`, `reg add` / `reg import`, `New-ItemProperty` / `Set-ItemProperty` / `New-Item` / `Set-Item` on `HKCU:` / `HKLM:` / `Registry::` / `Env:` paths, `[Environment]::SetEnvironmentVariable`, registry `SetValue`, `Win32_Environment` / `wmic environment`, `launchctl setenv`, `export`, `$env:` and `set` assignments. Reads such as `rg`, `echo $env:…`, `reg query` and `Get-ItemProperty` stay allowed. A commit message or file write that merely mentions the name next to one of those verbs is also denied — use your editor. Configure the flag yourself outside agent sessions.

### Ask audit (RAD-190 R5)

Cursor 3.23 on Windows runs `permission: ask` with no dialog, so an `ask` is an allow in practice. Every decision that returned `ask` before RAD-190 is now a deliberate `allow` or a `deny`. With `PRGENIE_GITHUB_GATE_ASK` unset, the gate returns only `allow` or `deny`. When a human sets the flag, each **deny** row below returns `ask` again; **allow** rows stay `allow`.

Rows that were already `deny` under RAD-188 (`export_local_pr`, `record_export_gate_override`, `gh_use`, shell publish verbs from a loop agent, empty or unparseable stdin) keep the same escape-hatch behaviour. The loop-agent denies (RAD-163) and the escape-hatch setter deny never become `ask`.

### Cursor hook delivery (RAD-185)

On Windows (verified 2026-10), Cursor passes the hook payload on **stdin** as UTF-8 JSON, often with a leading **UTF-8 BOM** (`EF BB BF`). There is no separate env var or temp file for the payload; argv is only `node`, the hook script, and (for diagnostics) a channel tag. PR Genie strips the BOM before `JSON.parse`, reads stdin asynchronously via `process.stdin` (same pattern as MCP stdio), and logs MCP gate lines under `.git/agent-console/before-mcp-execution.jsonl` (timestamp, raw byte count, read error, normalized tool name — not secrets). Workspace paths may arrive as `/c:/Users/…`; the gate normalizes those before resolving the git root. **Known host limit:** if Cursor stops delivering stdin entirely, every gated call is **denied** (fail closed, RAD-188 R4) until the host is fixed — documented here, not a product bug in PR Genie.

## Recommended setup

1. **Keep your normal `gh auth login`** for interactive work (export, org admin, creating repos). Use that login when _you_ run `/export` or fix account binds.
2. **Mint a fine-grained personal access token (PAT)** limited to **this repository** only:
   - **Contents** — Read and write
   - **Pull requests** — Read and write
   - **Workflows** — Read and write
   - **Actions** — Read-only
   - Expiration — **90 days or less** (rotate on a calendar reminder)
3. Export it for loop sessions only:

   ```bash
   export GH_TOKEN=github_pat_...
   ```

   Cursor loop agents inherit `GH_TOKEN` when the plugin runs `gh` / `git push` prep. Your broad OAuth login stays in the keyring for human export.

Fine-grained tokens cannot create or delete repositories or change org settings, which matches what loops need: commits, PRs, and CI on the working repo.

## Rotate the token

1. GitHub → **Settings → Developer settings → Fine-grained tokens** → select the PR Genie token → **Regenerate** (or create a new token and delete the old one).
2. Update `GH_TOKEN` in your shell profile or Cursor env and restart Cursor so hook/MCP processes pick it up.
3. Run `prgenie doctor` and confirm **gh-token-scopes** is green.

## OAuth apps and passwords

Changing your GitHub password does **not** revoke OAuth apps or classic tokens already issued to `gh`. After a credential incident, revoke stale **OAuth authorizations** and **personal access tokens** under GitHub settings, then `gh auth login` again for your human login.

## What the hook blocks

The github-gate hook treats a shell command as a loop agent's when it comes from a PR Genie subagent, from a `.loops/<id>` worktree, or from the primary checkout while a live loop has a steward binding. For those it denies:

- repo administration: `gh repo create/delete/edit/rename/archive/unarchive/fork`;
- mutating `gh api` calls (explicit `-X`/`--method`, or implied POST from `-f`/`-F`/`--field`/`--raw-field`/`--input`, attached or not) against `user/repos`, `orgs/*/repos`, `repos/{owner}/{repo}` and its `transfer`/`forks`/`generate` endpoints, plus GraphQL repo lifecycle mutations;
- `gh auth` (except `gh auth status` without `--show-token`), `gh secret`, `gh variable`, `gh ssh-key`, `gh gpg-key`;
- `gh alias set/import/delete` and `gh extension install/upgrade/exec`, which could rename or wrap a denied command;
- force-push (`--force`, `-f`, `--force-with-lease[=…]`, `--force-if-includes`, `--mirror`, or a `+` refspec) whose destination is the default branch or `main`, and deleting the default branch. Any other `git push`, `gh pr create` / `merge`, `gh repo create` or `gh release create` / `upload` / `edit` / `delete` / `delete-asset` from a loop agent returns **`deny`** with panel/CLI export guidance (RAD-188).

**Scope (RAD-190 loop-only scope).** These shell publish and repo-management denies apply **only to loop agents**. Loop detection is the RAD-163 one: a PR Genie subagent type (`prgenie-implementor`, `prgenie-implementor-strong`, `prgenie-reviewer`), the steward skill in the payload, a hook cwd (or its git root) inside a `<repo>.loops/lp-xxxxxxxx` worktree (or any subfolder of one), or a primary checkout whose `stewards.json` binds a live loop (or cannot be read). The global denies (PR Genie CLI human-only subcommands, the `PRGENIE_GITHUB_GATE_ASK` setter) are checked **before** the loop-target scan, so a long command cannot delay them. A command run from elsewhere that would be denied in a loop is then scanned for the directories it acts in, and is a loop agent's when any of them is a loop worktree (or inside one) or a repo with an active steward loop: `cd` (including cmd `cd /d`), `chdir`, `pushd`, `Set-Location` / `sl` / `Push-Location` (`-Path`, `-LiteralPath`; value parameters such as `-StackName` are skipped); `git -C` (chained `-C` resolved cumulatively, as git does), `--git-dir` / `--work-tree` (a `<repo>/.git/worktrees/<id>` admin dir maps to its worktree through its `gitdir` file, or by name); `GIT_DIR=` / `GIT_WORK_TREE=` and PowerShell `$env:GIT_DIR=` / `$env:GIT_WORK_TREE=`; `env -C` / `--chdir`; `sudo -D` / `--chdir`; `Start-Process -WorkingDirectory` (any unambiguous prefix; pwsh 7.6 has no alias for it) and cmd `start /d`. `builtin cd` / `command cd` and `git -c core.worktree=<dir>` count too. Relative paths resolve against every directory the shell context may be in. A `cd` inside a POSIX `( … )` subshell, a `$( … )` substitution, a nested `bash -c` / `cmd /c` script, a `for` / `while` / `until` body or a PowerShell scriptblock does not carry a run-time directory to later commands; a brace group `{ …; }` does. When the `cd` target is the loop variable of a literal `for d in a b` / `foreach ($d in a, b)` / `@(a, b)` list, each list word (globs expanded against the filesystem; no match keeps the word, as bash does) is a candidate target, and in a POSIX loop the candidates carry past `done`, so `for d in packages/*; do (cd $d && pnpm build); done; git push` is a normal agent's push while `{ cd <loop>; }; git push` and `(cd <loop> && git push)` deny. Each target is checked as written and by its real path, so a symlink or junction to a loop worktree (or to its `.loops` folder) is a loop target, and so is a hook cwd that is a link to one. The scan works on the tokenizer's unquoted, unescaped words (`git pu''sh`, `git p"u"sh`, `git pu\sh` are `git push`) and uses sets, so it is linear in the command. It **fails closed** with its own message (the target directory was decided at run time, so the gate cannot tell it is not a loop; spell the path out literally and retry) when a target only known at run time reaches a `git` / `gh` command in the same shell context (`cd "$(git rev-parse --show-toplevel)" && git push`, `git -C "$PWD" push`, `Set-Location $PSScriptRoot; git push`), when `CDPATH` appears anywhere in the command (inline, exported or `$env:CDPATH`) and a `cd` reaches a push, for a bare `cd`, `cd ~` or `cd -` when `HOME` or `OLDPWD` is assigned or exported in the command, for `find -execdir` / `-okdir`, and past its bounds (4096 possible working directories, 16384 targets or 200000 path resolutions; measured: about 180 relative `cd`s in one chain (`cd d0 && … && cd d179 && git push` allows, 190 fails closed) or about 16,000 absolute ones). Everything else is a normal agent, which may `git push`, `gh pr create`, `gh pr merge`, `gh repo create`, `gh release create` and `gh api -X POST` normally. The PR Genie CLI human-only denies, the `PRGENIE_GITHUB_GATE_ASK` setter deny and the MCP export / delete / `clear_loop_cancel` / approve-type denies stay **global**. Fail-closed crash handling and the too-complex budget also stay global and deny outside a loop: the gate cannot know what an unparsed command does, so it cannot tell it is not `prgenie export` or a setter. `Start-Process git -ArgumentList 'push',…` is read as the `git push` it launches. `git push --help` and `git push -h` only print usage and stay `allow` (RAD-190 R3).

For **every** agent shell command (loop or not), the human-only PR Genie CLI subcommands `prgenie export`, `prgenie gh use` (also `prgenie github use`) and `prgenie export-gate-override` return **`deny`** with the same panel/CLI guidance (RAD-190 R1). The gate looks for a PR Genie launch at **every word position** of each simple command (the way it finds `git push` and `gh`), after cmd `^` / PowerShell backtick escapes are removed. A launch is: the bin (`prgenie`, `prgenie.cmd`, `prgenie.ps1`, `prgenie.exe`, a path to it, Deno `npm:prgenie`); `pnpm cli …`, `pnpm run cli …`, `npm run cli -- …`, `yarn cli …`, `pnpm prgenie …`; `pnpm exec` / `pnpm dlx` / `npm exec` / `npm x` / `yarn dlx` / `yarn exec` / `bun x` / `npx` / `pnpx` / `bunx` with `prgenie` or `@prgenie/cli` (after their flags, including `--filter`); `npx -c '…'`; `corepack pnpm …`; and a CLI script word (`<path>/prgenie.cjs`, `<path>/cli.js` / `.cjs` / `.mjs`, or `packages/cli/src/bin.ts` / `cli.ts`) under any runner, including `node --import tsx`, `pnpm tsx` and `npx tsx`. Because every position is checked, prefixes and launchers (`call`, `start /b`, `xargs`, `find -exec`, `setsid`, `flock`, `env -S`, `su -c`, `strace`, `busybox`, …) and runner switches with values (`pwsh -wd C:\repo -c`, `powershell -ExecutionPolicy Bypass -c`, `cmd /v:on /c`, `bash -o pipefail -c`) do not hide it, and scripts given to `cmd /c`, `pwsh -c` / `-Command`, `bash -c`, `eval` and `iex` are checked too. `Start-Process` / `saps` / `start` is read as the command line it launches: the program from `-FilePath` (or the first positional) and the list from `-ArgumentList` / `-Args` / an unambiguous prefix such as `-Arg` (or the second positional), in any order, split on commas and spaces. The whole simple command is read, with no word, argument or occurrence cap. Parameters bind the way PowerShell 7.6 binds them (`(Get-Command Start-Process).Parameters`): exact names and aliases first (`-Path` / `-PSPath`, `-Args`, `-RunAs` = `-Credential`, `-RSO` / `-RSE` / `-RSI`, `-ea`, `-wa` = `-WarningAction`, `-ev`, `-wv`, `-iv`, `-ov`, `-ob`, `-pv`, `-infa`, `-proga`, and the switches `-lup`, `-nnw`, `-vb`, `-db`, `-wi`, `-cf`), then unambiguous prefixes; a value parameter's value is skipped with it, and an ambiguous prefix (`-e`, `-W`, which PowerShell refuses) is read both ways. A repeated `-ArgumentList` is checked both joined and one list at a time; a literal array (`@('export','lp-1')`, `@("export";"lp-1")`, `('export','lp-1')`) is read as its items. The launched command line then gets the same full scan as any other command, so prefixes inside it (`Start-Process env -ArgumentList 'A=1','prgenie','export'`, `sudo`, `timeout`), runner scripts (`Start-Process pwsh -ArgumentList '-c','echo x; prgenie export'`) and a run-time program with a literal human-only first argument (`-FilePath $exe -ArgumentList 'export lp-1'`, `-RSO o.txt $exe 'export lp-1'`, `$exe @('export','lp-1')`, `-FilePath (Get-Command prgenie).Source`, `((…).Source)`, `(Get-Command prgenie)`, `(…)[0].Source`, `('prg'+'enie')`) are denied, while `-FilePath $p -ArgumentList 'status'` / `'doctor'` stay `allow`. The same run-time-program rule covers the call and dot-source operators (`& $exe export`, `. $exe export`, `& (Get-Command prgenie) export`). For this check only, PowerShell groups are rewritten before the scan: a literal list in parentheses becomes its items, any other `(…)` / `@(…)` in word position becomes one run-time word (its inner command is still checked), and a `;` inside `@{…}` does not end the command (`-Environment @{A='1';B='2'}`), also in a script quoted after `pwsh -c` / `iex`; the check reads the command both with and without that rewrite, so it can only add denies. `watch` without `-x` joins its arguments and runs them with `sh -c`, so that script is checked like `bash -c` (`watch -n1 echo x ';' prgenie export` and `watch 'prgenie export'` are denied, `watch echo prgenie export` is a mention); `watch -x` / `--exec` runs its first word, like `xargs`. `xargs prgenie` with no literal subcommand (`echo export lp-1 | xargs prgenie`, `xargs -a f prgenie`) is denied as a run-time subcommand; `xargs prgenie status` stays `allow`. The scan is linear in the command length and has a deterministic work budget (characters re-read plus words scanned, 8M units; everyday commands such as a 200KB `git commit -m`, a 100KB `pwsh -Command` script or 2000 `--filter` flags use under 6%), with a 5s clock only as a backstop for a slow or loaded machine. When either runs out the command is denied as too large or nested to check (fail closed), for every agent, loop or not; that message tells the agent to retry in smaller pieces (`git commit -F file` instead of a huge `-m`, a script file, or several shorter commands) and that splitting it does not permit human-only PR Genie actions, which stay blocked; the human is told the agent can rerun it as smaller commands. Rebuilt Start-Process lines are charged to the budget when they are scanned; the Start-Process-in-Start-Process nesting itself is bounded by the 5s clock (RAD-190 R6). A 200KB command, including Start-Process forms with long argument lists and quoted script arguments, answers in under 2s through the built gate (most shapes in well under a second). Leading CLI flags are skipped (`prgenie --verbose export`), and a run-time subcommand (`prgenie $SUB`) or a run-time command word followed by `export` (`$P export lp-1`) is denied; the run-time message says the subcommand was decided at run time. A simple command whose **program** is data-only is a mention and stays `allow`: `echo`, `printf`, `Write-Host` / `Write-Output`, `rg` / `grep` / `findstr` / `Select-String`, `cat` / `type` / `Get-Content`, and `git commit` / `log` / `show` / `grep` / `tag` / `notes` / `add` / `diff` / `status`. The program is the word actually run, after prefix wrappers and their options and values (`sudo -u x`, `env -C dir`, `timeout 5`, `call`, `xargs -n 1`, `watch -x`) and, for a shell or evaluator, the first word of its script (`cmd /c echo …`, `pwsh -c "Write-Host …"`, plain `watch echo …`). A data word elsewhere (`sudo -u cat prgenie export`, `flock /tmp/cat prgenie export`, `find . -name cat -exec prgenie export …`) does not hide a launch. Read-only subcommands (`ci`, `doctor`, `list`, `status`, `show`, `gh status`, `gh list`, …) stay `allow`. A scoped package name (`@prgenie/cli`) is not a PowerShell splat, so filter builds (`pnpm --filter @prgenie/cli --filter @prgenie/core build`, `pnpm -F @prgenie/cli -F @prgenie/core test`) stay `allow`; a splat (`@a`, `@args`) or `@(…)` / `@{…}` is read as run-time.

The command is tokenized (POSIX and PowerShell quoting), so chains, pipes, `(…)`/`{…}` groups, `$(…)` and backtick substitutions, and `<(…)` process substitutions are each checked. Flags before a subcommand (`gh auth -h github.com token`) are skipped the way gh's own lookup skips them.

Heredoc and here-string bodies are data (only `$(…)` inside an unquoted body is checked), so a commit message that mentions `gh repo create` is not denied.

### Scripts run by a shell or evaluator

The runners are `bash`/`sh`/`zsh`/`dash`/`ksh`/`fish`, `pwsh`/`powershell`, `cmd`, `eval`, `iex`/`Invoke-Expression`, and `source`/`.`. A script they run is checked as commands when its text is in the command:

- an argument: `bash -c '…'`, `pwsh -Command '…'`, `cmd /c …`, `eval '…'`, `iex '…'`;
- stdin: a heredoc, `<<<` or here-string (`bash <<'EOF'`, `bash -s`, `pwsh -Command -`, `pwsh -`), or text piped from `echo`, `Write-Output`, a plain `printf` (no `%` or `\`), a single quoted string (`'…' | iex`), or `cat <<'EOF'`;
- a process substitution of those emitters: `bash <(echo '…')`, `source <(echo '…')`.

Loop agents are denied when a runner's script is not in the command text:

- a variable or expansion: `bash -c "$CMD"`, `eval "$CMD"`, `iex $cmd`, `iex @args`, `source "$f"`, `. $env:X`, `cmd /c %CMD%`, `bash <<< "$CMD"`, `echo "$CMD" | bash`, `$x | iex`, `$'…'`;
- command output or a subexpression: `bash -c "$(curl …)"`, `eval $(…)`, `Invoke-Expression (Get-Content x -Raw)`, `pwsh -Command (…)`, `curl … | sh`, `Get-Content x | iex`, `( … ) | iex`, `'a'+'b' | iex`;
- a file or process substitution: `bash < file`, `cat file | bash`, `bash <(curl …)`, `source <(cat x)`, and a script-file argument that is a variable (`bash "$SCRIPT"`);
- escapes or formatting that would have to be decoded: `printf` with `%` or `\` in the format, `echo -e`, any `\` in echoed text, PowerShell backtick escapes, and an unquoted heredoc containing `$` or backticks;
- `pwsh`/`powershell -EncodedCommand` (`-enc`, `-ec`, `-e`), always.

Static script files (`bash script.sh`, `pwsh -File x.ps1`, `source ./env.sh`) are allowed; the hook does not read files.

The same rules apply to a runner behind a prefix command, after its options, option values (separate, attached like `-ux`, or after a short cluster like `-iu x`) and leading operands are skipped: `sudo`, `doas`, `runuser`, `env` (including `VAR=x`), `nice`, `timeout <duration>`, `stdbuf`, `ionice`, `chrt <priority>`, `taskset <mask>`, `command`, `exec`, `nohup`, `time`, `&` and `wsl` (for example `timeout 60 nice -n 5 sudo -u x bash -c "$CMD"` is denied, and `timeout 60 git status` is not).

A runner started by a launcher is checked too:

- `xargs` / `parallel`: the input (stdin, or `parallel`'s `:::` / `::::` / `:::+` arguments) is appended to the runner's arguments, so the runner is denied when it has no script of its own (`xargs bash -c`, `xargs sh`, `xargs eval`, `parallel bash -c ::: "$CMD"`), when its script contains the replace string (`xargs -I{} sh -c '{}'`), or when the input would land in the script text (`xargs pwsh -Command`, `xargs cmd /c`). A literal `xargs bash -c '…' _` is checked like `bash -c '…'`;
- `find -exec` / `-execdir` / `-ok` / `-okdir`: denied when the runner's script contains `{}` or is missing (`-exec sh -c 'run {}' \;`, `-exec bash {} \;`); a literal script is checked;
- `Start-Process` / `saps` / `start`: denied when the program is only known at run time or a runner's `-ArgumentList` contains a variable, subexpression or splat; a literal argument list is checked as one command (`Start-Process bash -ArgumentList '-c','…'`).

Other commands that run under these launchers (`xargs rm`, `find … -exec grep … {} +`, `Start-Process notepad`) are unaffected.

Loop agents must spell `gh` commands literally. A command word that is only known at run time (`$GH`, `$(…)`) is treated as `gh`/`git`. A `gh` command group or subcommand built at run time (`gh $SUB create`, `gh $(echo repo) delete`, `& gh @(…)`), `gh` launched through `xargs` or `Start-Process`, a `gh api` method or endpoint from a variable, and a GraphQL query read from a file (`query=@file`, `--input`) are all denied.

The primary folder counts as a steward context when `stewards.json` names a live loop. If that file exists but can't be read, the hook fails closed and gates the primary folder.

The hook is a guard rail, not a sandbox. The fine-grained `GH_TOKEN` above is the real boundary. Known limits — host delivery and run-time evaluation the hook cannot see:

- **A normal agent can publish (RAD-190 loop-only scope):** outside a loop the gate no longer denies `git push` or `gh` publish / repo-management commands. The fine-grained `GH_TOKEN` (or whatever credential that agent has) is the only boundary there; give agents a token scoped to what they may publish.
- **Loop detection limits (RAD-190 loop-only scope):** a loop agent is recognised by its payload (subagent type, steward skill), its cwd, or a literal target listed in the scope paragraph above (symlinks and junctions are followed: each target is checked both as written and by its real path). Not caught:
  - a `cd` or push inside a script another program runs: a script file or package script, `watch 'cd <loop> && git push'` (run by `sh -c`), `git -C <loop> rebase --exec 'git push' HEAD~1`, `git submodule foreach` scripts beyond the literal `git push`, git hooks;
  - a directory fed in at run time by another program: `echo <loop> | xargs -I{} git -C {} push`;
  - git aliases: `git -C <loop> -c alias.p=push p`, `git config alias.p push && git -C <loop> p`;
  - pushing the loop's branch by name from the primary checkout (`git push origin lp-abcdef12`, after `git -C ../repo worktree list` or not), or from a new worktree or clone of it (`git worktree add ../w2 lp-abcdef12 && cd ../w2 && git push`): only the directory is checked, not the branch;
  - `Start-Process -WorkingDirectory` passed through a splat hashtable built earlier (`$p=@{WorkingDirectory='<loop>'}; Start-Process git push @p`), `Invoke-Command` / `Start-Job` script blocks;
  - loop bodies: the only loop value read is a **literal list word, after brace expansion (`{a,b}`, nested, `{1..3}`, `{a..c}`, steps; more than 4096 words fails closed, as does a list word that is itself run-time, `$(ls …)` or backticks, when the body `cd`s to it outside a subshell, unless the next `cd` in that body is `cd -` or a `popd` straight after `pushd`; a bare `cd ..` does not count, so `for d in $(ls packages); do cd $d; …; cd ..; done; git push` still denies for a normal agent: use a subshell or a glob). A POSIX `{` / `}` is a brace group only as a standalone word in command position; `{x,y}` anywhere else is brace-expanded (an escaped `\{x,y\}` is still expanded, which can only over-deny) and glob expansion against the filesystem, used directly as the `cd` / `pushd` / `Set-Location` / `Push-Location` target** (`for d in <words>; do cd $d; done`, `foreach ($d in <words>)` / `@(<words>)`, nested loops included; a POSIX body's `cd` carries past every enclosing `done`). Anything else in a loop body that sets the directory from a run-time value does not carry and is not failed closed: composed targets (`cd $d/lp-…`, `cd ../repo.loops/$d`, `e=$d; cd $e`), positional `for d;` (after `set --`), `select`, C-style `for ((…))` bodies with run-time paths, `while read d`, PowerShell pipelines with `$_` (`@('<loop>') | ForEach-Object { Set-Location $_ }`, `… | % { … }`), `(Get-Item '<loop>').FullName` / `$d.FullName`, and `foreach ($d in Get-ChildItem …)`;
  - bounds that fail closed for a normal agent: a glob list matching more than about 4096 directories denies a later push even when the body only `cd`s in a subshell, and roughly 1000 repeated list loops before a push deny on the work budget; past a scan bound the targets found so far are checked as written only (not through symlinks), so such a deny may say "decided at run time" rather than name the loop;
  - Windows-only path forms are not exercised by the Linux tests (`\\?\C:\…\repo.loops\lp-…`, drive-relative `cd C:foo`);
  - `gh -R owner/repo` naming the loop's GitHub repo, and a loop agent payload Cursor does not label (no subagent type, cwd outside the loop). A steward loop is recognised only while `stewards.json` binds a live local PR.
- **UTF-8 BOM on hook stdin (Windows):** Cursor may prefix JSON with a BOM; PR Genie strips it. If a future host build omits stdin, the gate fails closed (`deny`) rather than allow (RAD-185, RAD-188).
- **Cursor 3.23 on Windows ignores `ask` (RAD-188, verified 2026-10-08, Cursor 3.23.23):** Live hooks logged `permission: ask` for agent `export_local_pr` and `git push --dry-run`, Cursor recorded a valid hook response, and the action still ran with **no confirmation dialog**. The same build **enforces `deny`**. Treat `ask` as non-blocking on this host; human-only actions use `deny` by default.
- **MCP export timeout:** The MCP stdin reader applies `notifications/cancelled` as soon as the frame is complete, without waiting for the active `tools/call`, and aborts that request's in-flight `export_local_pr` / `run_ci` signal. A stdin error aborts in-flight controllers the same way. Cursor may still drop the MCP session on idle timeout (`-32001 Request timed out`) before long export finishes; that idle timeout is a host limit. Heartbeats and the raised `mcp.json` timeout (RAD-100) mitigate but do not guarantee the host waits forever.

- script files are not read: an agent can write `gh repo delete` into a file and run `bash x.sh`, `pwsh -File x.ps1`, `source x`, `node x.js` or `python x.py`;
- other interpreters and programs are not modelled (`python -c`, `node -e`, `perl -e`, `ruby -e`, `make`, package scripts, git hooks and aliases, `curl` to the REST API with the token);
- for the RAD-163 loop and `gh` checks, launchers and prefixes not listed above (for example `su -c`, `runuser -c`, `env -S`, `script -c`, `watch`, `Invoke-Command`, `Start-Job`, `ssh`, `docker exec`, `cmd /c start`) are not unwrapped (the PR Genie CLI check scans every word, so it does see them);
- a pre-existing gh alias or extension, or a `gh` shim earlier on `PATH`, runs under a harmless-looking name;
- shell features outside the tokenizer (functions or aliases defined earlier in the session, `IFS` tricks, unusual quoting) can hide a command;
- PR Genie CLI wrapper forms the gate cannot see (RAD-190 R4): `pwsh -EncodedCommand` outside a loop (loop agents are denied any `-EncodedCommand`); a program name assembled at run time without a literal subcommand next to it (`$P $SUB`, `Start-Process $exe -ArgumentList $a`); splatting (`$p=@{FilePath='prgenie';ArgumentList='export lp-1'}; Start-Process @p`); a one-element array written with a leading comma (`Start-Process $exe -ArgumentList @(,'export')`, `(,'export')`); .NET process APIs (`[Diagnostics.Process]::Start('prgenie','export lp-1')`) and other PowerShell method calls (`(Get-Command prgenie).Invoke(…)`); `iex $s` where `$s` holds a script assigned earlier (a here-string or any variable); `xargs prgenie <literal words>` whose input adds more words (`echo lp-1 | xargs prgenie gh`, only a bare `xargs prgenie` / `xargs prgenie gh` is denied); a script file or package script that runs it (`bash x.sh`, `pnpm run my-export`, a `package.json` script other than `cli` / `prgenie`); an interpreter loading the CLI module (`node -e "require('…/prgenie.cjs')"`, `python -c`); a renamed or copied entry (`node x.cjs export`); a shell alias or function (`alias pg=prgenie; pg export`); a data-only program that itself runs a command it is given (`rg --pre prgenie`, `LESSOPEN='|prgenie export …' less f`); and any CLI process started by a program the hook does not model (`make`, git hooks), including git configuration and environment strings that git executes: `GIT_EDITOR` / `core.editor` (`git commit`, `tag -a`, `notes add`), `GIT_PAGER` / `core.pager` / `pager.<cmd>`, `git -c alias.x='!…'`, `diff.external` with `--ext-diff`, `git grep -O` / `--open-files-in-pager`, and `core.hooksPath`. The same strings can run `git push`. The cmd `^&` escape is not understood by the tokenizer, so `echo ^& prgenie export` is a harmless over-deny. The PowerShell `(…)` / `@(…)` / `@{…}` reading is done by the PR Genie CLI check only (the command text, scripts quoted after `pwsh` / `powershell` / `iex`, and reconstructed Start-Process lines, at most three levels deep); the RAD-163 `git` / `gh` checks still use the shared tokenizer, which splits on a `;` inside `@{…}`. `find -exec prgenie export {} \;`, `deno run npm:prgenie`, `pnpm tsx` / `npx tsx …/bin.ts` and `Start-Process` with `-ArgumentList` **are** covered (every-position scan);
- cmd `^` escapes inside `git` / `gh` words (`gi^t push`, `git pu^sh`) are not removed for the publish and loop checks (they are for the PR Genie CLI check). PowerShell backticks there already deny (``gi`t push``, ``git pu`sh``);
- other CLI subcommands that mirror denied MCP tools are not denied from the shell (R1 covers only `export`, `gh use`, `export-gate-override`): `prgenie approve`, `prgenie status <id> approved|reviewed`, `prgenie delete`, `prgenie delete-learning`, `prgenie comment --role human`, and `prgenie steward <id> --restart` / MCP `steward_next` `restart: true`, which still clear a cancel marker until RAD-186 R0 lands;
- the `PRGENIE_GITHUB_GATE_ASK` setter deny (RAD-188 R5) only sees the name as static text: a name built at run time (string concatenation, variables, base64), a `.reg` file or script that holds it, or a writer reached through an interpreter (`python -c`, `node -e`) without the literal name, is not caught.

See **RAD-163** and `packages/cli/src/loop-github-gate.ts`.

## Doctor

`prgenie doctor` warns when `gh auth status` shows classic scopes such as `repo`, `delete_repo`, `admin:*`, or `workflow` on the active token — scopes broader than loops need. Point the fix at this document and switch loop work to `GH_TOKEN`.
